Projet Iniwave · Infrastructure

Un VPS, un seul point d'entrée, des réseaux qui s'ignorent

Odoo, n8n et deux autres projets tournent sur le même serveur, chacun dans son réseau Docker isolé. Traefik est le seul point d'entrée public. Et même quand deux services partagent la machine, ils se parlent parfois via internet plutôt qu'en interne — c'est exactement ce que montre ce schéma.

routage Traefik standard appel qui boucle par l'IP publique port publié en direct, hors Traefik réseau Docker isolé

Pourquoi ce détour compte

n8n et Odoo tournent côte à côte, mais ne se voient pas

odoo-iniwave_default et le réseau de n8n sont deux réseaux Docker distincts, créés séparément par deux docker compose différents. Aucune route interne ne les relie : n8n ne peut pas simplement appeler http://odoo:8069.

Il appelle donc https://odoo-iniwave.luluplug.com/jsonrpc — exactement comme le ferait un client externe. La requête sort du serveur, repasse par le DNS public, revient sur le port 443, et c'est Traefik qui la route vers le bon conteneur.

C'est ce qui rend le pattern directement transférable à NetSuite : que l'ERP soit sur la même machine ou à l'autre bout d'internet, n8n lui parle de la même façon — API REST/JSON-RPC en HTTPS, aucune hypothèse de réseau partagé.

Un quatrième chemin, assumé

Pourquoi le dernier nœud lit la base Postgres directement

Ce n'est pas un besoin de performance — la démo ne manipule que quelques enregistrements. Deux raisons précises : montrer la compétence (SQL/PostgreSQL est listé dans la fiche de poste), et vérifier indépendamment ce qui a été créé — l'API dit « facture créée » en parlant d'elle-même, la requête SQL relit directement la table pour confirmer que la facture existe, avec le bon client.

Pour s'y connecter, n8n utilise le port Postgres publié à part (:5433) — un chemin qui contourne Traefik entièrement, sans TLS. Choix assumé pour cette démo ; en production, n8n et Odoo partageraient un réseau Docker interne, sans exposer ce port du tout.
